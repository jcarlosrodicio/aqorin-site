// the problem

Your engineering process is trapped inside one agent's config folder.

Every coding agent ships its own agents, commands, skills, hooks and permission model. The moment you write a real workflow — spec, implement, review, fix — it only exists in one runtime, and it is enforced by a prompt asking the model to remember.

// how it works

Aqorin owns the semantics. Runtimes own the execution.

The Orchestration Engine keeps the Run: its state, its policies and its evidence. Runtime Adapters translate each step into whatever the runtime does natively. A runtime is never the source of truth.

one Run, one source of truth adapters: add a runtime without touching Core

// the identity at the center

A reviewer is a role. Not a runtime. Not a model.target · TV5

Roles, runtimes and models are independent concepts. The goal: specify with one runtime, implement with another, review with a third model — inside the same Run, with the same rules. Today a Run uses one runtime and one model for every role; mixing them is exactly what the validation track is testing.

// non-negotiables

Built on rules the engine enforces, not ones a model should remember.

01

Never touches your config

Aqorin projects an isolated, namespaced Configuration Overlay. Your agents, commands, skills and MCP setup are never overwritten or deleted.

02

Your native UX stays

Keep running opencode, pi or codex as you do today. Use Aqorin only when you want orchestration.

03

Invariants in code

Phase order, iteration budgets, required review, approval gates and legal transitions live in a reducer — not in a system prompt.

04

State belongs to the Run

A runtime session is an attempt, not the Run. Events are durable, so a crashed runtime does not erase what happened.

05

Honest guarantees

Every permission is labelled: runtime-native, Aqorin-enforced, OS-sandboxed, external — or not enforceable. No silent elevation, ever.

06

No lowest common denominator

Use a runtime's strongest primitive natively; emulate safely; degrade visibly; or refuse to run. Features are not removed for symmetry.

// where it really stands

The thesis is not proven yet. Here is the experiment.

Aqorin is only worth building if a user can define a runtime-independent workflow once, and Aqorin runs it durably across runtimes and models — mixed in one Run — without special-casing the workflow. Before growing the product, a Thesis Validation Track tests exactly that, on macOS (Apple Silicon) with OpenCode, Pi and Codex.

what exists today

  • Durable Run/Event core with a reducer that refuses success without passed validations
  • Five Runtime Adapters; the built-in feature workflow ran live once on each, separately, on macOS arm64
  • @aqorin/cli@0.2.0 on npm (MIT) — it lags the main branch
  • Not claimed: user workflows, mixed runtimes per Run, Linux or Windows support
