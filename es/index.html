Aqorin es una capa de orquestación independiente del runtime para agentes de código. Defines una vez cómo se especifica, implementa, valida y revisa el trabajo. OpenCode, Pi, Codex, Claude Code o jcode lo ejecutan. Tu configuración sigue siendo tuya.

// el problema

Tu proceso de ingeniería está atrapado en la carpeta de configuración de un agente.

Cada agente de código trae sus propios agentes, comandos, skills, hooks y modelo de permisos. En cuanto escribes un workflow real —especificar, implementar, revisar, corregir— solo existe en un runtime, y lo sostiene un prompt que le pide al modelo que se acuerde.

✕ hoy

  • "Pide siempre una revisión antes de terminar" vive en un prompt
  • Cambiar de runtime obliga a reescribir el workflow
  • Una sesión que se cae se lleva consigo el estado
  • "¿Esto está en sandbox?" — nadie sabe decir dónde se aplica

// cómo funciona

Aqorin es dueño de la semántica. Los runtimes, de la ejecución.

El Orchestration Engine custodia el Run: su estado, sus políticas y su evidencia. Los Runtime Adapters traducen cada paso a lo que el runtime hace de forma nativa. Un runtime nunca es la fuente de verdad.

un Run, una única fuente de verdad adapters: añade un runtime sin tocar el Core

// la identidad central

Un reviewer es un rol. No un runtime. No un modelo.objetivo · TV5

Rol, runtime y modelo son conceptos independientes. El objetivo: especificar con un runtime, implementar con otro y revisar con un tercer modelo, dentro del mismo Run y con las mismas reglas. Hoy un Run usa un único runtime y un único modelo para todos los roles; mezclarlos es justo lo que está probando el track de validación.

// innegociables

Reglas que aplica el engine, no reglas que el modelo debería recordar.

01

No toca tu configuración

Aqorin proyecta un Configuration Overlay aislado y con espacio de nombres propio. Tus agentes, comandos, skills y MCP nunca se sobrescriben ni se borran.

02

Conservas tu UX nativa

Sigue usando opencode, pi o codex como hoy. Recurre a Aqorin solo cuando quieras orquestación.

03

Invariantes en código

Orden de fases, presupuestos de iteración, revisión obligatoria, puertas de aprobación y transiciones legales viven en un reducer, no en un system prompt.

04

El estado es del Run

Una sesión del runtime es un intento, no el Run. Los eventos son durables: si el runtime se cae, lo ocurrido no se pierde.

05

Garantías honestas

Cada permiso lleva etiqueta: nativo del runtime, aplicado por Aqorin, sandbox del SO, externo… o no aplicable. Nunca se elevan permisos en silencio.

06

Sin mínimo común denominador

Usa de forma nativa la mejor primitiva de cada runtime; emula con seguridad; degrada de forma visible; o se niega a ejecutar. No se quitan funciones por simetría.

// dónde está de verdad

La tesis aún no está demostrada. Este es el experimento.

Aqorin solo merece la pena si un usuario puede definir una vez un workflow independiente del runtime y Aqorin lo ejecuta de forma durable con distintos runtimes y modelos —mezclados en un mismo Run— sin casos especiales en el workflow. Antes de hacer crecer el producto, un Thesis Validation Track prueba exactamente eso, en macOS (Apple Silicon) con OpenCode, Pi y Codex.

qué existe hoy

  • Un core durable de Runs y eventos, con un reducer que rechaza el éxito sin validaciones superadas
  • Cinco Runtime Adapters; el workflow feature integrado se ejecutó en vivo una vez en cada uno, por separado, en macOS arm64
  • @aqorin/cli@0.2.0 en npm (MIT); va por detrás de la rama principal
  • No se afirma: workflows de usuario, runtimes mezclados en un Run, soporte para Linux o Windows
